# 🧠 ГЛОБАЛЬНІ ПРАВИЛА ДЛЯ АГЕНТІВ (AGENT_RULES)

Ці правила є обов'язковими для виконання всіма ШІ-агентами, що працюють над цим проєктом.

## 🛑 1. Controlled Refactoring Policy

1. Заборонено видаляти або перейменовувати файли без плану.
2. Якщо зміна торкається:
   - DB моделей
   - статусів документів
   - posting logic
   - register logic

   Агент повинен:
   - надати план змін
   - показати список файлів
   - описати ризики
   - отримати підтвердження

3. Видалення або перейменування дозволене ТІЛЬКИ:
   - якщо доведено, що код не використовується
   - або якщо заміна повністю сумісна

4. Заборонено "переписувати з нуля".
   Дозволено: рефакторинг з мінімальними diff-змінами.

## ✅ 2. ЩО МОЖНА РОБИТИ БЕЗ ПИТАННЯ
- Додавати нові файли, функції, компоненти, стилі.
- Розширювати існуючий код (нові поля, методи, кнопки), не чіпаючи старе.
- Виправляти очевидні синтаксичні помилки, якщо це не змінює логіку.

## 🎯 3. ІНКРЕМЕНТАЛЬНІ ЗМІНИ — НЕ ПЕРЕПИСУЙ ТЕ, ЩО ПРАЦЮЄ
- **НЕ МОЖНА:** видаляти сторінку/компонент і писати «з нуля» без команди.
- **НЕ МОЖНА:** повністю змінювати структуру HTML/CSS без дозволу.
- **ТРЕБА:** додавати нове поряд зі старим.
- **ТРЕБА:** використовувати Feature Flags (прапорці функцій) для приховування/показу нового коду.
- **ТРЕБА:** один запит — одна логічна зміна.

## 🤔 4. ПРАВИЛО ГНУЧКОСТІ
- Ти маєш право запропонувати порушення правил, якщо це об'єктивно покращить код.
- **Порушення можливе ТІЛЬКИ після прямого підтвердження користувачем.**

## 🎨 5. СТИЛЬ ТА АДАПТИВНІСТЬ
- Усі сторінки мають коректно відображатися на мобільних пристроях (≤640px).
- Використовуй Flex/Grid, уникай фіксованої ширини.
- Кнопки на мобільному — на всю ширину.
- Дотримуйся існуючої кольорової гами та відступів у проєкті.

## 🗄️ 6. РОБОТА З БАЗОЮ ДАНИХ
- Нові поля — обов’язково `nullable=True` або `default`.
- Ніколи не видаляй колонки, які вже використовуються.
- Індекси — на всі зовнішні ключі.
- Міграції Alembic — окремий файл на кожну зміну.

## 💬 7. КОМУНІКАЦІЯ
- Перед виконанням складного завдання запропонуй план (Implementation Plan).
- Показуй результат у браузері після кожної зміни.
- Якщо зробив помилку — визнай і запропонуй виправлення.

## 🚀 8. ПУШ НА GITHUB ТА СИНХРОНІЗАЦІЯ
- Після кожної логічної зміни або виправлення багу, агент **ОБОВ'ЯЗКОВО** має надати команди для `git push`.
- Агент не може сам пушити (якщо не має прямого доступу), але має готувати готові команди для користувача.
- Завжди нагадуй користувачу зробити `git pull` на сервері Vultr після пушу.
## 🧱 9. Controlled Refactoring Policy (керований рефакторинг)

Мета: дозволити розвиток системи без поломки фундаменту.

### 9.1 Change Levels (рівні змін)

**Level 0 — Safe Additive (без підтвердження)**
Дозволено без питань:
- додавання нових файлів/ендпоїнтів/компонентів
- додавання нових nullable полів або полів з default + міграція
- додавання нових тестів
- виправлення багів без зміни контрактів API

**Level 1 — Local Refactor (потрібен план, без підтвердження)**
Дозволено після короткого Implementation Plan (3–7 кроків):
- винести логіку з routes у services
- розділити великі файли на менші
- прибрати дублювання коду шляхом винесення helper/service
- перейменування *внутрішніх* змінних/функцій без зміни API/DB

**Level 2 — Contract Change (потрібне підтвердження користувача)**
Тільки після підтвердження:
- будь-яка зміна DB схеми (крім additive nullable/default)
- будь-які зміни API контрактів (поле/тип/назва/роут)
- перейменування файлів/компонентів/ендпоїнтів
- зміни document lifecycle / posting / registers
- зміни auth/roles

**Level 3 — Breaking / Migration (потрібен окремий план + підтвердження)**
Тільки окремим таском:
- об’єднання таблиць (наприклад, unified documents)
- видалення колонок/таблиць/volume
- масові рефактори across modules
- зміна інфраструктури деплою

---

### 9.2 Refactor Protocol (як довести, що фундамент не ламається)

Для будь-якого рефакторингу Level 1+ агент ОБОВ’ЯЗКОВО надає:

1) **Before/After Contract Check**
- які API контракти не змінюються
- які DB таблиці/поля не змінюються

2) **File Impact List**
- список файлів, які змінюються

3) **Rollback Plan**
- як повернутися назад (git revert / previous commit)

4) **Verification Checklist**
Мінімум:
- docker compose up -d
- alembic upgrade head (якщо були міграції)
- перевірка ключових endpointів (200 + expected response)
- перевірка ключових UI сторінок без console errors

---

### 9.3 Forbidden Without Explicit Approval
Заборонено без підтвердження:
- змінювати document lifecycle (DRAFT/POSTED/UNPOST)
- робити auto-posting при створенні
- змінювати posting rules або структуру AccumulationRegister
- змінювати назви ключових сутностей (Order/Invoice/Receipt) у публічному API
